## Platform

web

## Users

พิธีกร (MC) หนึ่งคน เป็นผู้ควบคุมแอปเองบนโน้ตบุ๊กที่ต่อกับโปรเจกเตอร์ ระหว่างกิจกรรมประมูลของรางวัลช่วงเย็นวันที่ 4 (คืนสุดท้ายที่ผู้เข้าร่วมทุกคนยังอยู่พร้อมกัน — วันที่ 5 เป็นแค่ครึ่งเช้าแล้วเดินทางกลับ) ของโครงการ Training for the Trainers (TFT) ไม่มีผู้ใช้อื่นที่โต้ตอบกับตัวแอปโดยตรง — ผู้เข้าร่วมงาน (ผู้ประมูล) เห็นเฉพาะจอที่ฉายผ่านโปรเจกเตอร์ ไม่ได้แตะอุปกรณ์เอง

## Product Purpose

เครื่องมือควบคุมการประมูลของรางวัลแบบสด สำหรับกิจกรรมปิดท้ายโครงการ TFT ที่ผู้เข้าร่วมสะสม token/เหรียญ/สติกเกอร์จากการตอบคำถามหรือเข้ากลุ่มระหว่างบรรยายตลอดโครงการ แล้วนำ token มา "ประมูล" แลกของรางวัลในงานเลี้ยงคืนสุดท้าย คู่กับช่วงเฉลยคู่บัดดี้ ความสำเร็จของแอปคือช่วยให้พิธีกรควบคุมจังหวะการประมูล (แสดงรูป/ราคา/เพิ่มราคา/เคาะขาย) ได้ลื่นไหลกลางงานเลี้ยงโดยไม่สะดุด และสร้างบรรยากาศสนุก/มีชีวิตชีวาให้ผู้ชม

## Positioning

ต่างจากซอฟต์แวร์ประมูลทั่วไป (ที่มักต้องมีบัญชีผู้ใช้ อินเทอร์เน็ต หรือให้ผู้ประมูลหลายคนกดจากอุปกรณ์ตัวเอง) ตรงที่ออกแบบเฉพาะรูปแบบของงานนี้: พิธีกรคนเดียวกดแทนผู้ประมูลที่ตะโกน/ยกมือในห้อง (ไม่ใช่ผู้ประมูลกดเอง), ต้องทำงานได้ 100% แบบออฟไลน์ในสถานที่จัดเลี้ยงที่ไม่แน่ใจสัญญาณเน็ต และเป็นไฟล์เดียวเปิดได้ทันทีไม่ต้องติดตั้ง/ล็อกอิน

## Operating Context

- ใช้ครั้งเดียวในงานเลี้ยงเย็นวันที่ 4 (1 ต.ค. 2569) ของโครงการ TFT (จัดทั้งหมด 28 ก.ย. – 2 ต.ค. 2569) ช่วงเฉลยบัดดี้
- อุปกรณ์: โน้ตบุ๊กเครื่องเดียวของพิธีกรต่อกับโปรเจกเตอร์/จอฉาย ไม่มีอุปกรณ์ผู้ใช้อื่นเชื่อมต่อระบบ
- ไม่มีอินเทอร์เน็ต/Wi-Fi ที่เชื่อถือได้ในสถานที่จัดงาน ต้องรันได้แบบออฟไลน์ทั้งหมด (เปิดไฟล์ตรง ๆ ด้วยเบราว์เซอร์ ไม่มี server)
- รายการของรางวัลจริง (รูป + ราคาตั้งต้น) ยังไม่ถูกส่งมา ผู้ใช้แจ้งว่าจะส่งให้ภายหลัง — ตอนนี้ใช้ข้อมูลตัวอย่าง (sample items) แทนชั่วคราว
- เป็นส่วนปลายทางของกลไก token สะสมที่ใช้ตลอดโครงการ (วิทยากรแจก token ตอนถามตอบ/กิจกรรมกลุ่มระหว่างบรรยาย ก่อนหน้านี้)

## Capabilities and Constraints

- ไฟล์ HTML เดี่ยว (self-contained) ไม่มี build step, ไม่มี dependency ภายนอก, ไม่มี CDN/Google Fonts — เปิดได้ด้วยการ double-click ตรง ๆ
- เก็บสถานะ (รายการของรางวัล/ราคา/ผู้ชนะ) ด้วย `localStorage` พร้อม try/catch กันพัง (บาง origin/บาง sandbox บล็อก storage — เจอจริงระหว่างทดสอบ)
- 3 หน้าจอ: ตั้งค่ารายการของรางวัล (เพิ่ม/แก้/ลบ, แนบรูปจากเครื่อง), ประมูลสด (เต็มจอได้ด้วยคีย์ `F`, ซ่อนปุ่มควบคุมด้วย `H`), สรุปผล + export CSV
- เสียงเอฟเฟกต์สร้างด้วย Web Audio API (ไม่มีไฟล์เสียงแนบมากับแอป), แอนิเมชันฉลองตอน SOLD (ค้อนเคาะ + confetti บน canvas) เขียนเอง ไม่พึ่ง library ภายนอก
- คีย์ลัดอิงตำแหน่งปุ่มจริงบนคีย์บอร์ด (`e.code`) ไม่ใช่ตัวอักษรที่พิมพ์ได้ (`e.key`) เพราะพิธีกรอาจสลับเลย์เอาต์ภาษาไทย/อังกฤษระหว่างงาน
- ยังไม่ตัดสินใจ: จะแยกจอควบคุม (พิธีกร) กับจอแสดงผล (โปรเจกเตอร์) ออกจากกันแบบ sync ข้ามหน้าต่างหรือไม่ — ปัจจุบันเลือกรวมเป็นจอเดียว (ปุ่มควบคุม + จอแสดงผลอยู่ด้วยกัน) เพื่อความเสถียร หลีกเลี่ยงความเสี่ยงเรื่อง sync บน `file://`

## Brand Commitments

- ชื่อในแอป: "ประมูลของรางวัล — TFT" ผูกกับโครงการ TFT เดียวกับเว็บคู่มือหลัก แต่เป็นเครื่องมือคนละชิ้นคนละกลุ่มผู้ใช้ — ไม่ใช้ระบบดีไซน์เดียวกับ DESIGN.md ของเว็บคู่มือที่ root (นั่นสงวนไว้เฉพาะเว็บคู่มือสาธารณะ)
- ธีมภาพที่ตกลงไว้แล้วกับผู้ใช้ก่อนลงมือสร้าง: แนว "Night Gala" (พื้นเข้ม + ทอง) สำหรับจอที่ฉายให้ผู้ชมเห็น ให้ความรู้สึกเหมือนเวทีประมูลการกุศลตอนกลางคืน ไม่ใช่ปาร์ตี้เด็กเล่น

- ยังไม่มีรูปภาพ/รายการของรางวัลจริง — ใช้ emoji + ข้อมูลตัวอย่าง 4 รายการแทนไปก่อน ห้ามถือเป็นของจริงในงานนี้

## Product Principles

- ความเสถียรมาก่อนความสวยงาม: ฟีเจอร์ใดก็ตามที่เพิ่มความเสี่ยงต่อการพังกลางงาน (เช่น พึ่งอินเทอร์เน็ต, sync หลายหน้าต่าง) ต้องถูกตั้งคำถามก่อนเสมอ
- พิธีกรต้องกดง่ายแม้ในที่แสงน้อยหรือกำลังพูดสด — ปุ่มใหญ่ คีย์ลัด ไม่มีขั้นตอนซับซ้อน
- จอที่ผู้ชมเห็นต้องดูสะอาด ไม่มี UI ควบคุมกวนสายตา ให้ความรู้สึกเหมือนเวทีประมูลจริง
- ใช้งานครั้งเดียวจบสำหรับงานนี้ ไม่ต้องออกแบบให้ scale เป็นระบบประมูลทั่วไปเกินความจำเป็น

## Accessibility & Inclusion

ยังไม่มีข้อกำหนดที่ยืนยันชัดเจน — จอแสดงผลตั้งใจให้ตัวเลข/รูปมีขนาดใหญ่พอมองจากระยะไกลในห้องแสงสลัวได้ เป็นการตัดสินใจเชิงดีไซน์ ไม่ใช่ requirement ที่มีผู้ระบุมา
